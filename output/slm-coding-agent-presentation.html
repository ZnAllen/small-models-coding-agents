小模型做 Coding Agent

如何用 7B 以下 的小型語言模型

📌 什麼是小型語言模型（SLM）？

🔹 定義

通常指 7B 參數以下 的開源語言模型。常見家族：
Qwen2.5-Coder、DeepSeek-Coder、Phi、LLaMA

🔹 為什麼用它？

  • 成本低（訓練 + 推論都便宜）
  • 可部署在邊緣裝置（筆電、手機）
  • 延遲低、隱私友好

🔹 主要挑戰

  • 推理能力較弱
  • 工具呼叫容易出錯
  • 多步任務容易崩潰

核心問題：SLM 不像 GPT-4 那樣「懂的很多」，但透過正確的架構與提示策略，仍然可以做出有用的 Coding Agent。

Wiki 來源：model-capabilities.md · small-model-tool-calling-problems.md

⚠️ SLM 工具呼叫的六大核心問題

P1 格式遵循困難

JSON 結構錯誤、引數缺失；即使 fine-tune 後仍是最大失敗原因。

P2 工具選擇錯誤

不需要時執意呼叫（false positive）、選錯 tool。

P3 多步驟崩潰

nested calls、多輪協調表現遠遜大模型；1B 模型多輪後成功率 <40%。

P4 過度擬合

SFT on finite data 傾向 memorize pattern，而非學習泛化規則。

P5 上下文受限

累積 token 後效能急降，multi-turn conversation 特別嚴重。

P6 Hallucination

Hallucinate 不存在的 tool，或過度依賴既有知識忽略 actual schema。

📊 不同尺寸的 SLM 能做到什麼程度？

級距代表模型Code Gen工具呼叫適合任務
≤1BQwen-0.5B, DeepSeek-1.3B~33–40%需 SFT，多步極差單一指令、領域專精
3BQwen2.5-Coder-3B, Phi-3-mini~57–72%可接受（SFT 後）基礎程式碼生成、單步 FC
7BQwen2.5-Coder-7B 🏆, LLaMA-3.1-8B~82–87%良好；TinyAgent-7B > GPT-4-turbo多步推理、複雜編程 agent

💡 關鍵發現：3B→7B 提升 ~30pp，遠大於 0.5B→3B。顯示 7B 是實用最低門檻。（arXiv:2507.03160）

Wiki 來源：small-model-code-gen-benchmarks.md · 參考資料：arXiv:2507.03160、2409.00608

🛠️ 解法一：面向小模型的提示工程

✅ 結構化模板 + 引導解碼

把輸出格式預先定義為固定 template，配合 guided decoding 限制 token 生成空間為有效 JSON/AST。

<tool_call> tool_id: [number] arguments: {...} </tool_call>

效果：Mistral-7B BFCL 66.5 → 71.4

✅ 分階段提示 + Few-Shot

拆成三步：意圖分類 → 工具選擇 → 參數填充

難度遞增排列示例；覆蓋邊界案例（false positive/negative）；1B 模型 2–3 個 examples 即可。

🎯 核心原則：「降低推理負擔」——透過結構化輸出格式、分階段思考、以及上下文管控，讓小模型在有限預算內發揮最大潛力。

Wiki 來源：prompt-engineering.md · 參考資料：arXiv:2509.18076

🧩 解法二：Plan-Execute 解耦架構

根據 arXiv:2608.22472：sub-3B 模型是優秀的「指令 Following者」而非「規劃者」。

👤 使用者請求
→
🧠 Planner
(SRM 1–2B) 解析意圖、生成計劃
→
⚡ Executor
(Main SLM 3–7B) 逐階段執行 + context 隔離
→
📦 最終回應

Context 隔離

每步只有必要最小 context，避免累積噪訊。

角色專精

SRM 只需理解 tool semantics，不需強大 code gen。

容錯性高

單步失敗不影響全局，可 retry specific steps。

Wiki 來源：hybrid-systems.md · 參考資料：arXiv:2608.22472

🗂️ 解法三：ToolRAG 與上下文管理

🔍 ToolRAG 動態檢索

上百個工具時不要全放 prompt（會淹沒 SLM）。

  • User query → embed → 搜尋 top-K 相關工具
  • 僅將 K 個工具納入 prompt
  • 輸入長度減少 60%+

🧠 上下文壓縮策略

  • 每 N 步觸發 summarization prompt
  • 保留結論，捨棄中間細節
  • 滑動視窗只保留最近 M 步

📌 實務建議：先用 ToolRAG 將 prompt 控制在 1500 tokens 以內；context usage >70% 自動觸發摘要。

Wiki 來源：memory-context.md · 參考資料：TinyAgent（arXiv:2409.00608）

⚙️ 解法四：量化、剪枝與 RL 後訓練

技術原理速度增益精度損失適用場景
GPTQ-4bit權重量化到 4-bit≈3×中等記憶體緊張的部署
AWQ-4bit保留重要權重的 4-bit 量化≈3×較小weight distribution 敏感的模型
FP88-bit 浮點，NVIDIA GPU 硬體加速≈1.8×最小NVIDIA 設備（H100 等）
GRPO（RL）Group Relative Policy Optimization—改善 accuracy進一步提升 tool-use

最佳實踐順序

先剪枝→再量化，組合減速可達 4–6×，精度損失可控在 3–5pp 內。

RL 穩定性提醒

直接對小模型做 RL training 極度不穩定（arXiv:2602.03022）；建議搭配 similarity-guided teacher refinement。

Wiki 來源：optimization.md · 參考資料：arXiv:2602.03022（STAR）

🎯 如何選擇？任務－模型配對決策

單一工具呼叫

規模 1.5B｜SFT + guided decoding
預期成功 70–80%

多輪工具協調

規模 7B 或 hybrid｜ToolRAG + plan-decoupling
預期成功 40–60%

單一函式程式碼生成

規模 3B｜Instruct tuning
預期成功 60–75%

多文件 refactoring

規模 7B｜SFT + RAG
預期成功 30–50%

倉庫級 coding agent

規模 7B+ 或 MoE｜完整 framework
預期成功 <30%

Edge 部署（終端裝置）

規模 ≤1.1B｜TinyAgent SFT + quantization
侷限指定領域
